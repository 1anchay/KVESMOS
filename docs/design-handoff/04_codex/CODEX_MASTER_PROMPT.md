# CODEX — KVESMOS: рабочий промпт для продолжения Flutter-проекта

Ты продолжаешь **существующее** приложение в локальном проекте `dududud` (прежнее название в интерфейсе: OrbitWords). Мы готовим его переименование в **KVESMOS** и последующее развитие как бесплатной образовательной игры. Ты НЕ создаёшь проект заново.

## Подтверждённое состояние (по прошлым сообщениям, перепроверь в репозитории)
- Android debug APK для arm64-v8a собран и **запускается на реальном Android**; пользователь прошёл первый урок. Сохраняется прогресс. Заявлено 20 уроков английского A1.
- Flutter / SDK на Windows настроены, debug сборка проходила. Локальная SQLite/Drift и тесты ранее работали. Flutter/iOS на Mac не проверены, Supabase на реальном сервере не подтверждён.
- **Известная проблема:** распознавание речи / микрофон на Android не работает. Некоторые функции пользователю кажутся странными; деталей ещё нет — не выдумывай баги без воспроизведения.
- Из прежнего статического аудита есть P1/P2: импорт новых уроков после обновления, защита привязки прогресса к аккаунту, статичные счётчики 20 уроков / 120 XP. Не смешивай правки этих областей с ребрендингом; занеси в план регрессий.

## Источник требований
Эта папка `KVESMOS_Codex_Handoff_v1` — дизайнерский handoff, НЕ готовые исходники Flutter. Обязательно прочитай **только** (1) `00_READ_FIRST/START_HERE.md`, (2) `02_design/BRAND_GUIDE_CURRENT.md`, (3) `02_design/CHARACTERS.md`, (4) `02_design/REWARDS_SPEC.md`, (5) JSON `03_data/kv_catalog_draft_v2.json` и при необходимости манифест. **Не обходи все PNG, если задача не касается графики.**

**Важное правило**: главный Орби — персонаж, который выглядывает из-за синей планеты, с большим голубым взглядом, космическим кольцом и подвесной жёлтой звездой. Подтверждение: `01_approved/orbi/orbi_confirmed_by_user_screenshot.png`. Исходная иллюстрация — нижняя правая из `orbi_icon_six_variants_original_sheet.png`. **Не заменять его любым другим роботом из набора!** Производное `orbi_selected_crop_REFERENCE_NOT_FINAL.png` — превью, не финальное высококачественное приложение и не прозрачный adaptive foreground.

Изображения большинства персонажей остаются **концепт-листами**. Однако теперь доступны дополнительные рабочие ассеты: **Пикси** (`01_approved/characters/pixie_sheet.png`), изолированные PNG трёх сундуков в `01_approved/chests/isolated/`, а также лист эмоций и 6 отдельных PNG Орби в `01_approved/orbi/emotions/`. Эти ресурсы можно использовать как стартовые UI-ассеты без генерации новых изображений. Взрослый профессор-лис утверждён визуально, но не имеет окончательного имени. Дизайн женского персонажа Веспы ~25 лет утверждён. Название KVESMOS пока предварительное: проверка прав/магазинов до релиза.

## Главная цель
Постепенно улучшить UX, добавить самостоятельный мультяшный бренд, персонажей, сундуки, косметику и красивый профиль, **не ломая обучение и офлайн-работу**. Не копировать дизайны, тексты и защищённых персонажей Duolingo / известных франшиз. Приложение остаётся абсолютно бесплатным: нет рекламных блокировок, подписок, энергии или платных сундуков.

## Работа строго этапами — не пытайся выполнить всё за один прогон

**Этап 0 — короткая техническая инвентаризация (без лишних правок)**
1. Посмотри `git status`, структуру основных файлов, зависимости, схему БД и существующие тесты. Если Git не настроен, просто зафиксируй текущие файлы и отсутствие репозитория; не инициализируй/не сбрасывай его без запроса.
2. Не затрагивай существующий Android `applicationId`, bundle identifier iOS, префиксы SQLite, ключи secure storage, Supabase URI / package name. Подготовь безопасный план ребрендинга: **сначала display name, строки и UI**. Без потери прогресса.
3. Обнови один файл статуса (`PROJECT_STATUS.md` или существующий `docs/STATUS.md`), если надо, с честным разграничением того, что проверено и что ещё нет.

**Этап 1 — устранение блокера микрофона (первая реальная задача)**
- Продиагностируй Android speech-to-text / permissions (manifest + runtime), наличие поддерживаемого системного сервиса, язык распознавания, отказ в доступе, сетевую зависимость/необходимость офлайн-моделей и ошибки плагина. Не обещай скачивание голосов/моделей без подтверждения.
- Сохрани текстовый fallback. Добавь понятное сообщение пользователю, если речь не поддерживается. Исправляй только воспроизведённый сбой, создай адресные тесты.
- Сохрани текущую работоспособность всех типов уроков и XP. После этого STOP и короткий отчёт. При возникновении неоднозначного отказа попроси у владельца нужный лог с телефона.

**Этап 2 — безопасный ребрендинг и UI (следующий отдельный запрос)**
- UI display name KVESMOS, палитра, тексты, упорядочение главной карты/экрана урока/результата/профиля. Читаемость, шрифты, состояния ошибок, reduced motion.
- Утверждённого Орби добавлять только из его референса; если качество вырезки недостаточно для финальной иконки — остановись на UI-прототипе и сообщи, что нужен отдельный финальный экспорт. Не пытайся генеративно пересоздавать маскота.
- Без миграции идентификатора пакета; если понадобится, сначала отдельный план по обновлениям Android/iOS и сохранности данных.

**Этап 3 — персонажи и каталог (отдельный запрос)**
- Каталог строго из `03_data/kv_catalog_draft_v2.json`, но **не предполагается**, что JSON прямо подходит к существующей схеме. Согласуй реальные модели с текущим кодом. Полные изображения из листов не использовать как готовые анимированные персонажи.
- На первом проходе 2–3 персонажа и простая галерея, остальное список/плашки. Не придумывай новые персонажи вместо утверждённых.

**Этап 4 — сундуки, косметика, инвентарь (отдельный запрос)**
- Чёткие ID, атомарные события выдачи, идемпотентность, повторное открытие не меняет результат, офлайн сохранение и корректная миграция SQLite.
- Три вида сундуков, 20 стартовых косметических предметов, четыре редкости. Правила шансов и исключения повторов — в `REWARDS_SPEC.md`. Показывать **фактические** шансы с нормализацией после исчерпания категорий. Нет денежной монетизации, влияния косметики на уроки и вынужденных задержек.
- Начать с базового сундука и одного визуального слота, затем расширять, не переписывая архитектуру. Если отдельные PNG недоступны — использовать чётко обозначенные временные UI-заглушки, но не заявлять финальный дизайн готовым.

**Этап 5 — визуальные детали и релизный QA (отдельный запрос)**
- Короткая пропускаемая анимация, реакция персонажа, редкости, удобство инвентаря, ручные QA-кейсы на Android.
- Без реального Supabase не выдавать облачный sync за проверенный. Для iOS перечислить действия на macOS, не изображать успешную сборку на Windows.
- Отдельно позже — новые языки и предметы. Сначала расширяемая архитектура каталога, без немедленного создания всех курсов.

## Эффективность и безопасность
- Не перечитывай всю кодовую базу перед маленькой правкой. Поиск по релевантным файлам, минимум диффа и зависимостей.
- Не изменяй базовую логику уроков/SM-2/XP без необходимости. Не обновляй автоматически 42+ старых пакетов только ради предупреждений.
- Запускай адресные тесты на каждом этапе, полный набор и Android сборку на контрольной точке. Не выключай значимые проверки ради экономии лимитов.
- Не делай из одного промпта 5 больших PR. После выполнения **этапа 1** остановись и доложи, что фактически проверено, а что требует Android-логов/ручного QA.
- Не удаляй пользовательский прогресс, не делай `flutter clean`/reset/DB-drop без обоснованной необходимости; не включай ключи и секреты в код/отчёты.
- Не создавай новую версию приложения «с нуля», не переименовывай классы/таблицы для красоты, не выдумывай подписи/иконки.
- Если сборка Gradle нуждается в дополнительном SDK, сначала проверь уже установленный локальный SDK. Не устанавливай все компоненты по одному без оценки полного списка.
